# Формат данных карты и правила отображения

Карта собирается из JSON. Можно держать всё в одном файле (`services: [...]`) или по файлу на сервис (объект с `sections`): `build_map.py` склеит их сам. Полный рабочий пример — `assets/example.json`.

## 1. Структура файла

```json
{
  "title": "Бэкапы судного дня",
  "subtitle": "Сбор критичных данных",
  "services": [
    {
      "id": "support", "name": "Поддержка", "icon": "chat",
      "sections": [
        {
          "id": "requests", "name": "Обращения и чат", "icon": "chat",
          "desc": "Обращения клиентов из ЛК, приложения и почты.",
          "components": [ ... ],
          "links": [ ["web", "gateway", "HTTPS"], ["tickets", "pg", "SQL"] ]
        }
      ]
    }
  ]
}
```

- **Сервис** — то, что видно в сайдбаре группой: «Поддержка», «Модерация».
- **Раздел** — пункт внутри сервиса со своей схемой: «Обращения и чат», «Телефония». Если у сервиса нет деления, сделайте один раздел с тем же именем.
- `id` — латиница, цифры, дефис. Уникален внутри уровня. Не меняйте id между пересборками: по нему сливаются файлы.
- `icon` для сервиса и раздела: `chat`, `book`, `phone`, `star`, `photo`, `flag`, `envelope`, `bell`, `shield`, `db`, `service`, `client`, `secret`, `cron`, `external`, `section`. Неизвестная — нейтральная пиктограмма.
- Корневую ноду раздела описывать не нужно: карта рисует её сама из `name` и `desc` раздела и ведёт от неё связи к точкам входа.

## 2. Компонент

```json
{
  "id": "pg",
  "layer": "data",
  "kind": "db",
  "name": "support_db",
  "tech": "PostgreSQL 16",
  "desc": "Обращения, переписка, SLA, метаданные вложений.",
  "sources": ["CMDB", "pg_dump --schema-only от DBA", "листинг doomsday/support/"],
  "items": [ ... ]
}
```

| Поле | Обязательно | Что писать |
|---|---|---|
| `id` | да | короткий, стабильный: `pg`, `tickets-api`, `s3-files` |
| `layer` | да | один из шести слоёв, см. раздел 3 |
| `kind` | да | тип, задаёт пиктограмму и цвет, см. раздел 4 |
| `name` | да | имя как в самой системе: имя базы в СУБД (`\l`, приглашение psql), бакета, деплоймента. Имена из CMDB, файлов дампа и разговоров — в `desc`. До 28 символов |
| `tech` | нет | технология и версия коротко: `PostgreSQL 16`, `Go`, `MinIO · 4,8 ТБ`. До 32 символов |
| `desc` | нет | одно предложение, зачем компонент нужен разделу. Человеческое название сюда, если `name` техническое |
| `sources` | желательно | откуда сведения: «CMDB», «Helm-чарт tickets-api», «Иван (DBA), чат 10.10». Показывается в карточке |
| `items` | для хранилищ — да | что внутри и есть ли в бэкапе, см. раздел 5 |

Компонент — это то, что работает или хранит данные само по себе: сервис, база, бакет, очередь, внешняя система. Таблица, крон, топик или секрет — не компонент, а объект внутри компонента.

## 3. Слои: что на какой уровень класть

Слои идут сверху вниз в этом порядке. Слой без компонентов на карте не показывается.

| layer | Подпись на карте | Что сюда |
|---|---|---|
| `entry` | Точки входа | откуда приходят люди и данные: веб, мобильное приложение, почтовый ящик как канал, телефонная линия, внешний партнёр, который шлёт запросы |
| `app` | Сервисы | то, что обрабатывает запросы онлайн: API, шлюз, Keycloak, АТС, workflow-движок |
| `bus` | Очереди и кеш | Kafka, RabbitMQ, Redis, NATS |
| `workers` | Фоновые задачи | консьюмеры, воркеры, крон-задачи, ETL |
| `data` | Хранилища | базы, поисковые индексы, бакеты, файловые шары, аналитические БД |
| `external` | Внешние системы | то, что раздел использует, но не владеет: почтовый сервер ИТ, СЭД, SMS-шлюз, FCM |

Слой выбирается по роли в этом разделе, а не по тому, какая команда владеет компонентом. Бакет с моделями, которым владеет ML-платформа, для раздела отзывов — его хранилище данных (`data`), владельца укажите в `desc`. `external` — для систем, данные которых разделу не нужно собирать: SMS-шлюз, FCM, чужой API.

Если компонент подходит под два слоя, выбирайте по роли в этом разделе. Пример: почтовый ящик Exchange, из которого воркер забирает письма, — `external`. Тот же ящик как канал, куда пишут клиенты, — `entry` (и тогда это разные компоненты: канал без данных и ящик с данными).

Крон: если у задачи есть свой код и деплой — это компонент в `workers` с объектом `cron` внутри. Если это строчка в crontab сервера — объект `cron` в компоненте этого сервера.

## 4. Типы компонентов (kind)

| kind | Когда | Цвет пиктограммы |
|---|---|---|
| `client`, `channel` | веб, приложение / почта, телефон | голубой |
| `gateway`, `service`, `auth`, `pbx` | шлюз, сервис, авторизация, АТС | синий |
| `queue`, `stream`, `cache` | RabbitMQ / Kafka / Redis | фиолетовый |
| `worker` | воркер, крон, ETL | мятный |
| `db`, `search`, `analytics` | СУБД / OpenSearch, Elastic / ClickHouse, DWH | жёлтый |
| `object` | S3, MinIO, файловая шара | розовый |
| `mail`, `external` | почтовый сервер / любая внешняя система | серый |

## 5. Объекты внутри компонента (items)

```json
"items": [
  { "type": "schema", "name": "tickets", "status": "yes", "where": "pg_dump → doomsday/support/tickets.dump",
    "children": [
      { "type": "table", "name": "tickets", "size": "12,4 млн строк" },
      { "type": "table", "name": "tickets_archive", "size": "61 млн строк", "status": "no", "note": "unlogged, в дамп не попала" }
    ] },
  { "type": "cron", "name": "sla-escalate", "status": "no", "note": "создан вручную в кластере, манифеста нет" },
  { "type": "secret", "name": "tickets-api/db", "status": "yes", "where": "снапшот Vault → doomsday/vault/" }
]
```

| Поле | Что писать |
|---|---|
| `type` | `schema`, `table`, `collection`, `bucket`, `topic`, `queue`, `cache`, `cron`, `config`, `secret`, `index`, `mailbox`, `file`, `volume`, `repo`, `other` |
| `name` | имя как в системе: `tickets`, `support-attachments`, `helm/tickets-api`, `/etc/asterisk` |
| `size` | объём, если известен: «12,4 млн строк», «4,8 ТБ», «64 файла». Только для понимания масштаба |
| `status` | `yes`, `no`, `skip`, `unknown`, см. раздел 6 |
| `where` | для `yes`: где лежит собранная копия. Путь или место, без дат и расписаний |
| `note` | для `no`, `unknown`, `skip`: коротко почему |
| `children` | один уровень вложенности: таблицы схемы, коллекции базы |

Правила:
- Дочерние элементы наследуют `status` родителя. Свой `status` указывайте только у исключений.
- Больше ~15 детей не показывайте: оставьте критичные таблицы, остальное одной строкой `{ "type": "table", "name": "… ещё 37 таблиц" }`.
- Расписание кронов, частоту бэкапов и дату копии не пишите. Это разовый сбор критичного: важно, что собрано и где лежит.
- Значения секретов никогда не копируйте: только имя секрета.
- Каждый объект живёт в одном компоненте, иначе он посчитается дважды. Общий секрет или конфиг кладите туда, где он хранится или кто его основной потребитель, а у остальных упомяните в `desc`.
- Не добавляйте объекты-заглушки «на всякий случай» («прочие схемы», «другие топики»): сомнение в полноте — это вопрос владельцу в отчёте, а не строка на карте. Исключение — компонент, про содержимое которого не известно ничего (см. `references/sources.md`).
- Сервис без своих данных оставляйте без `items`: на карте будет «Без данных». Если у него есть конфиг или секреты, без которых его не поднять, добавьте их объектами `config` и `secret`.

## 6. Статусы

| status | На карте | Когда ставить |
|---|---|---|
| `yes` | зелёный ✓ «В бэкапе» | есть подтверждение, что копия собрана: файл в хранилище, вывод утилиты бэкапа, письменное подтверждение владельца |
| `no` | красный ✕ «Нет бэкапа» | точно известно, что копии нет или объект исключён |
| `unknown` | фиолетовый ? «Не выяснено» | источник говорит «бэкапится», но подтверждения нет; источники противоречат; владелец не ответил |
| `skip` | серый — «Бэкап не нужен» | не критично: кеш, временные файлы, индекс, который пересобирается из базы. В `note` — из чего восстановится |

Сомневаетесь между `yes` и `unknown` — ставьте `unknown`. Карта нужна, чтобы найти пробелы, и ложное «в бэкапе» хуже честного «не выяснено».

Метка на ноде считается по всем объектам компонента (дети считаются вместо родителя):
- все `yes` → «В бэкапе N»;
- есть `no` и есть `yes` → оранжевая «3 из 5 в бэкапе»;
- только `no` → «Нет бэкапа N»;
- нет `no`, но есть `unknown` → «Не выяснено N»;
- только `skip` → «Бэкап не нужен»; нет объектов → «Без данных».

## 7. Связи

`[from, to, label]` или `{ "from": ..., "to": ..., "label": ... }`. Направление — «кто обращается → к кому»: сервис → база, воркер → бакет, шлюз → сервис. Для очередей: продюсер → очередь, очередь → консьюмер (так поток идёт сверху вниз).

- `label` — протокол или смысл в 1–2 слова: `SQL`, `REST`, `события`, `IMAP`. Показывается при выборе компонента.
- Связь внутри одного слоя рисуется сбоку, связь снизу вверх — допустима, но скрипт предупредит: чаще всего перепутано направление.
- От корня раздела к точкам входа связи рисуются сами.
- Компонент без связей — сигнал, что источник неполный. Выясните, кто к нему обращается.

## 8. Как это выглядит на карте

- Слева сайдбар: сервисы и их разделы. Красная цифра у раздела — сколько объектов не в бэкапе, фиолетовая «?N» — сколько не выяснено, зелёная галочка — всё критичное собрано.
- По центру — раздел сверху вниз: корень, затем слои в рамках с подписями. Нода: пиктограмма, `name`, `tech`, метка бэкапа.
- Справа без выбора — итог раздела и списки «Нет в бэкапе» и «Не выяснено». Клик по строке ведёт к компоненту.
- Справа при выборе — карточка: `desc`, объекты с отметками, `where` или `note` под каждым, «Откуда сведения», связи.
- Переключатель «Пробелы» оставляет яркими только компоненты с `no` или `unknown`.
- На ноде помещается около 24 символов имени и 30 символов `tech`, остальное обрезается многоточием.

## 9. Частые ошибки

- Таблица или крон заведены отдельным компонентом. Это объекты внутри базы или сервиса.
- Одна и та же база пришла из CMDB как `support-db-prod` и из Helm как `support_db`, и на карте два компонента. Слейте в один, оба источника в `sources`.
- `status: yes` по словам «вроде бэкапится». Это `unknown` с `note`.
- Расписание крона в `size` или дата копии в `where`. Для разовой акции не нужны.
- Связи нарисованы от базы к сервису. Направление — от того, кто обращается.
