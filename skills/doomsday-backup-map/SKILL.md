# Карта бэкапов судного дня

Результат — одна HTML-страница: слева сайдбар с сервисами и их разделами, по центру стек раздела сверху вниз (точки входа → сервисы → очереди → фоновые задачи → хранилища → внешние системы), у каждого компонента отметка, что из его данных собрано. Справа карточка: какие схемы, таблицы, кроны, бакеты внутри, где лежит копия или почему её нет, откуда сведения. Статусы «нет», «не выяснено» и «не нужно» владелец может поправить прямо на карте, а агент потом переносит правки в данные.

Это разовая акция по сбору критичного, а не мониторинг. Поэтому на карте нет расписаний, частоты бэкапов и дат копий: только «собрано / нет / не выяснено / не нужно» и где лежит копия.

**Когда:** собрать сведения о стеке сервиса из разрозненных источников и показать, что из критичных данных собрано; дополнить существующую карту новым сервисом или разделом. **Когда не брать:** нужен регулярный мониторинг бэкапов, план восстановления по шагам или обычная архитектурная схема без вопроса о бэкапах.

Работает в Claude (claude.ai, приложение, Cowork) и в агентах без артефактов — Codex, Claude Code. Отличается только то, как отдать готовую страницу (шаг 5).

## Файлы скилла

Пути — от папки этого скилла, в командах она обозначена `<скилл>`.

- `references/sources.md` — как разбирать разнородные источники, кому из них верить, как ставить статусы. Читайте перед разбором.
- `references/data-format.md` — формат JSON и правила отображения: что компонент, что объект, какой слой, какой статус. Читайте перед сборкой JSON.
- `scripts/build_map.py` — проверка данных и сборка страницы (Python 3, без зависимостей).
- `assets/map-template.html` — шаблон страницы, `assets/example.json` — полный пример на 3 сервиса и 8 разделов.
- `assets/template-src/` — исходники шаблона. Нужны, только если меняете вид карты, для сбора данных не читайте.

## Порядок работы

### 1. Принять исходники как есть

Пользователь даёт всё вперемешку: выгрузки, куски YAML, вывод команд, скриншоты, пересказ разговоров. Не просите переоформить — разбор ваша задача. Дайте каждому источнику короткое имя, оно пойдёт в поле `sources` компонентов.

Если не хватает базового — каких сервисов и разделов касается карта — спросите один раз. Остальные пробелы фиксируйте статусом `unknown` и вопросом владельцу, а не догадкой.

### 2. Разобрать в черновик

Пройдите источники по одному по рецептам из `references/sources.md` и ведите плоский черновик: раздел, компонент, объект, статус, где лежит копия или почему её нет, источник. Отдельно — связи «кто → к кому». Так видны дубли и противоречия до того, как они попадут на карту.

Главные правила разбора, потому что от них зависит, можно ли доверять карте:
- «В бэкапе» (`yes`) — только при подтверждении: файл в хранилище копий, отчёт утилиты бэкапа, письменное «собрано, лежит там-то». Слова «вроде бэкапится» и отметка в CMDB — это `unknown`. Ложное «в бэкапе» опаснее честного «не выяснено»: карту делают, чтобы найти пробелы.
- Не достраивайте недостающее. Нет списка таблиц — так и запишите (`note: "состав не выгружен"`), а не придумывайте типовые.
- Одна сущность под разными именами — один компонент, все источники в `sources`.
- Все подписи и описания — по-русски: названия сервисов, разделов и компонентов, `desc`, `note`, подписи связей. Латиницей остаются только имена из самих систем: базы, таблицы, бакеты, топики, кроны, секреты, переменные (`support_db`, `tickets_archive`, `DATABASE_URL`), а ещё названия продуктов и протоколов в `tech` и подписях связей (PostgreSQL, Kafka, SQL, REST). У сервиса `name` — что это для раздела («API обращений»), системное имя — первым в `tech` («tickets-api · Go»); у хранилища `name` — имя как в системе (`support_db`).
- Секреты только по имени. Значения, пароли и токены из источников не переносить никуда.

### 3. Собрать JSON

По `references/data-format.md`. Коротко:
- компонент — то, что работает или хранит само: сервис, база, бакет, очередь, внешняя система; таблица, крон, топик, секрет — объекты внутри компонента;
- слой по роли в разделе: `entry`, `app`, `bus`, `workers`, `data`, `external`;
- связи «кто обращается → к кому», для очередей продюсер → очередь → консьюмер;
- у объекта `status` и `where` (для `yes`) или `note` (для остальных); дети наследуют статус родителя;
- корень раздела не описывать, он рисуется сам.

Держите по файлу на сервис (`data/support.json`, `data/moderation.json`): так проще дополнять, когда приходят новые источники. `assets/example.json` — только образец формата: его компоненты и статусы выдуманы, ничего из него в реальную карту не переносите.

### 4. Проверить

```bash
python3 <скилл>/scripts/build_map.py data/*.json --check
```

Ошибки (битые связи, неизвестный слой, повтор id) исправьте. Предупреждения прочитайте: они ловят типичное — подписи не на русском, хранилище без объектов, `yes` без `where`, расписание или дату, просочившиеся из источника, связь снизу вверх, возможный дубль, очень длинное имя. Не каждое предупреждение — ошибка, но каждое стоит осознанного решения.

Скрипт печатает итог по разделам и список «не выяснено» — это готовые вопросы владельцам.

### 5. Собрать страницу и отдать

```bash
python3 <скилл>/scripts/build_map.py data/*.json -o map.html --title "Бэкапы судного дня"
```

Страница самодостаточна, но React и React Flow грузит с cdnjs и jsDelivr, поэтому открывается там, где есть доступ к этим адресам.

- **Claude с инструментом Artifact:** опубликуйте `map.html` как артефакт. При пересборке публикуйте тот же файл, чтобы ссылка не менялась. JSON-файлы отдайте файлами или сохраните в папку пользователя: по ним карту пересобирают.
- **Codex, Claude Code и другие агенты без Artifact:** оставьте `map.html` и JSON рядом в рабочей папке (например `doomsday-map/`) и назовите путь. Страница открывается двойным щелчком в браузере.

### 6. Коротко отчитаться

Две-три строки: сколько сервисов и разделов на карте, сколько объектов нет в бэкапе и сколько не выяснено. Затем вопросы владельцам, сгруппированные по людям или командам, если они известны:
- всё «не выяснено» из вывода скрипта;
- сомнения в полноте, которые не стоит рисовать на карте объектами («есть ли в базе другие схемы, кроме reviews?»);
- противоречия, которые не помещаются в карту, например расхождение дат в источниках;
- находки за пределами задачи: строки CMDB или манифесты других разделов, которые можно добавить следующим шагом.

Пересказывать карту не нужно.

## Правки статусов с карты

На карте у объектов со статусом «нет», «не выяснено» и «не нужно» статус меняется кнопкой справа от объекта. «В бэкапе» с карты не меняется: для него нужно подтверждение, где лежит копия, и оно вносится в данные. Правки сразу пересчитывают счётчики и хранятся в браузере того, кто их сделал (localStorage), — не на сервере и не у других зрителей.

Чтобы правки не потерялись, владелец нажимает в сайдбаре «Скопировать для агента» и присылает JSON. Сохраните его в файл и перенесите в данные:

```bash
python3 <скилл>/scripts/build_map.py data/*.json --apply changes.json -o map.html
```

Скрипт меняет статусы прямо в файлах данных, печатает, что применил и что не нашёл, и собирает страницу заново. После пересборки карта сама убирает из браузера правки, которые уже есть в данных. Если у объекта сменился статус, проверьте `note`: старая причина могла перестать подходить — уточните у владельца.

## Дополнение существующей карты

Новые источники или новый сервис: откройте нужный JSON, допишите или поправьте компоненты и объекты, оставив id прежними, и пересоберите. Статус меняйте, только когда есть подтверждение; в `sources` добавьте новый источник, старые не удаляйте. Если раздел пришёл целиком новым файлом, `build_map.py` сам вольёт его в сервис с тем же `id`.
